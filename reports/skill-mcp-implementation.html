00结论先行 EXECUTIVE SUMMARY

一句话结论

这套工具已经做完并且跑通了。它把前三份报告里最容易出错、最依赖人工查证的三件事 —— 目的国农残准入判断、到岸成本与平台费用测算、物流方案取舍 —— 变成了可被 AI 直接调用的标准化能力。代码在本机 tea-export-kit/，21 项验证全部通过（含真实的 MCP stdio 协议握手）。

已经能用的

出货前合规预检

输入目的国 + 本批次检测结果，直接输出 🚫 阻断 / ⚠️ 有风险 / ✅ 通过 三级结论，并列出必须先解决的动作。欧盟 0.01 检测限、蒽醌工艺来源、有机认证互认这些最容易踩的坑，都写进了判断逻辑。

已经能用的

成本与费用测算

到岸成本（含关税、附加费、隐性成本清单）与平台费用（亚马逊 $15 定价断点、Etsy 费率、Temu 品牌风险提示）都能一键算，输出费用拆解表与毛利率。

已经能用的

方法论文档化

三源交叉验证、关键词污染自检、买家背调五必查 —— 这些「怎么判断」的纪律被写进 Skill，换个会话、换个人用，结论口径不会漂。

四个关键判断

  1. 这套东西的价值不在「自动化」，在「防错」。跨境合规最贵的错误是「我以为能过」。工具把判断依据固化成规则，把「数据不足」显式暴露出来 —— 拿不到本批次检测报告时，它拒绝给出「通过」，而不是猜一个。
  2. 只借鉴设计模式，不复制代码。调研报告里点明：头部开源仓库（含 1302⭐、936⭐）多未声明许可证，商用有法律风险。本项目全部为原创实现，只吸收了「证据闸」「SKILL.md 目录结构」「三源交叉验证」这些方法论层面的做法，不涉及任何代码复用，因此没有许可证包袱。
  3. 数据可维护性是设计核心。所有准入数据、费率、物流参数都在 data/*.json 里，改 JSON 就能更新，不用碰代码。每条输出都自动附加数据版本号与免责声明，避免「半年前的结论当成今天的事实用」。
  4. 唯一的用户侧动作是「点一次信任」。工具装好、验证通过，但 MCP 出于安全设计不会自动激活。需要你在连接器管理页手动信任一次。这一步无法由程序代劳。
这份文档回答什么

① 这套功能的目标与适用场景；② 调研报告里哪些项目、哪些设计被真正用上了；③ 具体怎么实现、怎么装；④ 依赖什么、怎么配、怎么验证。

01核心目标与适用场景 GOAL & SCOPE

要解决的问题

调研报告的结论是明确的：GitHub 上约 70% 的跨境 Skill 围绕亚马逊运营（选品、Listing、广告、VOC），而「食品/农产品出口目的国准入」方向只有零星一两个，且都做中国国内标准（GB 7718、GB 2760），没有一个成熟的、面向出口目的国的工具。

这意味着：第一份报告里查到的欧盟 MRL 0.01、美国 FSVP、日本肯定列表、沙特 SFDA —— 目前没有任何现成工具帮你自动化。每次出货都要重新翻官方数据库、重新算一遍成本、重新判断物流，既慢又容易漏。

核心目标

把「出货前该查什么、怎么判断、算出多少钱」这条链路，从散落在报告和脑中的经验，固化成可被 AI 直接调用、输出带来源与日期的标准化能力。目标不是替代报关行或检测机构，而是让错误在出货前就暴露出来。

三个核心场景

场景一

出货前合规预检

触发：「这批茶能不能出到德国」「检测出啶虫脒 0.008 能过欧盟吗」
做什么：拉目的国准入要求 → 拿本批次检测结果比对高风险物质清单 → 给三级结论 + 待办清单 + 随货文件清单。

场景二

市场与成本验证

触发：「我的单丛该卖到哪个国家」「这个价还有多少利润」
做什么：三源交叉验证需求真伪 → 六维打分 → 用真实运费/关税算到岸成本 → 用平台费率反推定价与毛利。

场景三

买家与渠道尽调

触发：「这个海外买家靠不靠谱」「该不该接这个订单」
做什么：买家五必查项 + 红黄绿评级；渠道层面提示 Temu 这类伤品牌风险、亚马逊定价断点这类隐性坑。

适用与不适用

维度适用不适用

决策阶段出货前的合规预检、定价、物流选型、市场初筛替代报关行、检测机构、律师出具正式意见

3 个 Skill

合规

tea-export-compliance

三条铁律：0.01 是检测限不是安全线；蒽醌来自工艺不是农药（只能改烘干能源，改用药无效）；不合格的代价由进口商承担。含四步工作流与常见误判纠正。

选品

tea-market-selection

三源交叉验证（平台榜单 / 搜索趋势 / 供应链）+ 关键词污染自检（阈值 0.6）+ 六维打分。核心是避免被虚高搜索量误导 —— 「tea」在英文里还指茶歇、茶色。

尽调

tea-buyer-due-diligence

海外买家五必查项 + 红黄绿评级。用于「这个买家靠不靠谱」「该不该接这个订单」这类判断。

实际运行效果

下面是对欧盟、检出蒽醌与啶虫脒、且宣称有机的一批茶的真实调用输出（未做任何修饰）：

> check_compliance(market="EU", detected_compounds=["蒽醌","啶虫脒"],
                   organic_claimed=True, packaging_weight_kg=0.05)

# 合规预检 — 欧盟

## 结论：🚫 阻断

### 🚫 阻断项（必须先解决）
1. 检出 蒽醌（限量 0.02 mg/kg）— 非喷洒农药，由燃煤烘干与燃烧沉积物形成，
   是中国茶被欧盟通报的首要原因。应对（process）：改用电力/天然气/生物质
   等清洁能源烘干，减少烟尘接触
2. 检出 啶虫脒（限量 0.01 mg/kg）— 中国茶园常用，欧盟未给进口容忍量。
   应对（agronomy）：停用，改用合规替代药剂
3. 已宣称有机 → 必须持有 EU Organic 认证。注意：中国有机证书或 USDA NOP
   证书不能自动用于在欧盟等市场宣称有机，须由目的市场认可机构认证。

### ⚠️ 风险与待办
- 该市场默认 MRL 为 0.01 mg/kg，这是仪器检测下限而非毒理学安全值 ——
  只要检测得到即判不合格。多残留全项扫描不是可选项。
- 有机额外成本：有机检验费约 0.12–0.20 欧元/kg

### ✅ 已确认
- 单包净重 0.05 kg → HS 归类倾向 0902.10（绿茶）/ 0902.30（红茶·乌龙）
- 随货文件清单：该生产批次的农残检测报告（LC-MS/MS、GC-MS/MS 多残留方法，
  覆盖数百项）；原产地证；商业发票、装箱单、提单；有机茶：EU 认可机构的
  认证证书 + 经 TRACES 系统提交的检验证书（COI）

> 责任不对称提醒：一旦不合格，滞港、销毁、退运成本由进口商承担。

04依赖、配置与验证 DEPENDENCIES & VERIFY

依赖清单

依赖版本要求说明
Python≥ 3.10代码用到 list[str] | None 这类新式类型标注。本机环境为 3.13。
mcp≥ 2.3.0MCP 官方 Python SDK。随附 pydantic、anyio 等传递依赖。
标准库—其余全部使用标准库（json / pathlib / subprocess），零额外依赖。
一个容易踩的坑：mcp 2.x 的 API 变更

如果你在网上看到的示例是 from mcp.server.fastmcp import FastMCP，在 mcp 2.x 上会直接报 ModuleNotFoundError。v2.x 里 FastMCP 已更名为 MCPServer，正确写法是 from mcp.server.mcpserver import MCPServer。本项目已按新 API 实现，装的时候不用改。

配置要点

① MCP 配置项

写入 ~/.workbuddy-ai/mcp.json 的内容（脚本自动完成）：

{
  "mcpServers": {
    "tea-export": {
      "command": "<Python 解释器绝对路径>",
      "args": ["<kit 根目录>/mcp/tea-export-mcp/server.py"]
    }
  }
}

② 数据目录的相对位置不能动

服务端用 DATA_DIR = Path(__file__).resolve().parents[2] / "data" 定位数据。也就是说 server.py 必须待在 mcp/tea-export-mcp/ 下，data/ 在 kit 根目录。整个 kit 目录要一起移动，不能只挪 server.py。

③ 更新数据的方式

法规或费率变了，直接改对应的 data/*.json，把 _meta.version 升一位、compiled 改成当天日期，重启服务即可。不用碰 Python 代码。

④ 新增目的国市场

在 data/market-access.json 的 markets 下加一个键（如 KR），按现有结构填 name_zh / regulator / default_mrl_mg_kg / high_risk_compounds / documents / labeling 等字段。所有工具会自动识别新市场。

验证方式

两层验证，共 21 项断言，当前全部通过。

层验证什么断言数
L1 · 工具层 业务逻辑正确性：MRL 取值、三级结论判定、HS 分界、平台费率计算、物流推荐 16 项
L2 · 协议层 真实 MCP stdio JSON-RPC 握手：initialize / tools/list / tools/call，以及缺参数时服务不崩溃 5 项

L2 是关键 —— 它真的把服务端当子进程启动，按 MCP 协议发 JSON-RPC 请求，能抓到「函数本身写对了但协议接不上」这类只在集成时才会暴露的问题。
